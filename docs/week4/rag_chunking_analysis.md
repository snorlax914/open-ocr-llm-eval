# RAG 기반 Markdown Chunking 전략 분석

## 1. 분석의 출발점 — 이 프로젝트에서 청킹이 풀어야 할 문제

이 파이프라인은 **OCR이 만든 Markdown**을 입력으로 받고, 하류에는 (a) 카테고리 분류 LLM과 (b) RAG 검색이 붙는다. 분류 프롬프트([Prompt_0508.md](Prompt_0508.md))를 보면 다음 특징이 청킹 설계에 직접 영향을 준다.

- 분류 단서가 **문서 전체 맥락 + 핵심 키워드**(예: INVOICE, Country of Origin)에 흩어져 있음 → 한 청크가 핵심 단서를 모두 잃으면 분류 실패
- "단순 키워드 등장이 아니라 명확히 두 목적이 동시에 포함될 때만 다중 카테고리" 조건 → **하나의 문서가 여러 청크로 쪼개지면 '두 목적 동시 포함' 판단이 깨짐**
- 출력은 한국어 카테고리, 본문은 한·영 혼합 → 토큰 비용이 splitter별로 크게 달라짐
- 대상 문서가 무역·물류 문서(상업송장/포장명세서/선하증권/원산지증명서) → **표(품목·수량·금액·HS코드 등)가 본문의 핵심**

→ 청킹 평가축은 다음 5가지로 정리한다.
**(1) 표 보존 (2) 헤더/섹션 계층 보존 (3) 의미 단위 보존 (4) 토큰 효율 (5) 처리 속도/구현 난이도**

---

## 2. 현재 방식 점검 — RecursiveCharacterTextSplitter / 1500자 / overlap 200자

- **장점**: 별도 전처리 없이 작동, 문단/줄바꿈 우선 분할이라 자연스러움
- **약점 (이 프로젝트 한정)**:
  - **표가 1500자를 넘으면 행 중간에서 절단** — 송장·포장명세서의 품목 테이블이 가장 큰 위험
  - **섹션 소속 정보가 청크 메타데이터에 없음** — RAG 검색 결과에 "이 청크가 어느 헤더 아래인지" 표시 불가 → 분류 LLM에 줄 컨텍스트가 빈약
  - 문자 기준이라 한국어 토큰(1자 ≈ 1.5~2 토큰) 비용을 과소추정 — 1500자가 임베딩/LLM 측에서는 2,200~3,000 토큰이 될 수 있음
  - overlap 200자(약 13%)는 표 헤더 행 중복을 보장하지 못함

---

## 3. 4가지 Splitter 비교

### i. RecursiveCharacterTextSplitter
- **표 보존**: ✕ (큰 표는 행 중간 절단)
- **헤더 보존**: ✕ (메타데이터 없음)
- **의미 보존**: △ (separator가 문단·줄바꿈이라 어느 정도 자연 경계 유지)
- **토큰 효율**: △ (문자 기반, 언어별 편차 큼)
- **속도/난이도**: ◎ (가장 빠르고 단순)
- **이 프로젝트 적합성**: 평문 섹션에는 무난하지만 표·헤더가 중요한 무역 문서에는 단독 사용 부적합

### ii. MarkdownHeaderTextSplitter
- **표 보존**: △ (헤더로만 자르므로 표 자체는 안 잘리지만, 한 섹션이 너무 길면 후속 분할 필요)
- **헤더 보존**: ◎ (각 청크에 헤더 경로를 메타데이터로 자동 부착 — 예: `{"H1": "Commercial Invoice", "H2": "Items"}`)
- **의미 보존**: ◎ (섹션이 의미 단위인 문서에 한해)
- **토큰 효율**: △ (섹션 길이에 종속)
- **속도/난이도**: ○ (빠름, 단 OCR 헤더 마크업 품질에 의존)
- **이 프로젝트 적합성**: ◎ — 무역 문서는 "Shipper / Consignee / Description of Goods / Total Amount" 같은 섹션이 분류의 핵심 단서. 헤더 메타데이터를 분류 LLM 컨텍스트에 주입하면 [Prompt_0508.md](Prompt_0508.md)의 "key terms and overall context" 요건과 직접 부합
- **단, 전제 조건**: OCR 결과에서 `#`, `##` 마크업이 일관되게 생성돼야 함 → OCR 모델별 헤더 인식률 사전 확인 필수
- **권장 운용**: 단독이 아닌 **"MarkdownHeader → Recursive"의 2단 분할** (LangChain 공식 권장 패턴). 1차로 섹션 보존, 2차로 길이 제한

### iii. TokenTextSplitter
- **표 보존**: ✕ (토큰 한계만 보고 자름)
- **헤더 보존**: ✕
- **의미 보존**: ✕ (문장·표 행 가차없이 절단)
- **토큰 효율**: ◎ (임베딩/LLM 한계와 1:1 매칭)
- **속도/난이도**: ○ (단, tokenizer가 하류 모델과 일치해야 의미 있음 — Qwen tokenizer로 자르고 다른 임베딩에 넣으면 어긋남)
- **이 프로젝트 적합성**: △ — **단독 사용은 부적합**. 다만 Recursive/MarkdownHeader의 결과가 토큰 한계를 넘을 때 **"마지막 안전망"**으로 결합하는 용도로는 가치가 있음

### iv. SemanticChunker
- **표 보존**: ✕✕ (표 행은 의미 임베딩이 잘 잡히지 않아 엉뚱한 위치에서 잘림)
- **헤더 보존**: ✕
- **의미 보존**: ◎ (주제 전환 지점에서 자연스럽게 끊김)
- **토큰 효율**: △ (분할 결과 길이 불균일)
- **속도/난이도**: ✕ (모든 문장에 임베딩 호출 — 비용·지연 큼, threshold 튜닝 까다로움 — percentile/standard_deviation/interquartile)
- **이 프로젝트 적합성**: ✕ — 무역 문서는 표 비중이 높아 SemanticChunker의 약점이 직격. **비교군으로만 두고 메인 후보에서는 제외** 권장

## 4. 종합 비교표

| Splitter | 표 보존 | 헤더 보존 | 의미 보존 | 토큰 효율 | 속도 | 난이도 | 단독 적합도 |
|---|---|---|---|---|---|---|---|
| Recursive | ✕ | ✕ | △ | △ | ◎ | ◎ | △ |
| MarkdownHeader | △ | ◎ | ◎ | △ | ○ | ○ | ○ (하이브리드 필수) |
| Token | ✕ | ✕ | ✕ | ◎ | ○ | ◎ | ✕ (보조용) |
| Semantic | ✕✕ | ✕ | ◎ | △ | ✕ | △ | ✕ |

## 5. 잠정 권장안 (실험 전 가설)

**`MarkdownHeaderTextSplitter` (1차, 헤더·메타데이터 보존) → `RecursiveCharacterTextSplitter` (2차, 길이 제한, separator 우선순위에 표 행 구분자 `\n|` 포함) → 청크 길이 초과 시 `TokenTextSplitter` 안전망**

이 구조는:
- 분류 단서가 되는 섹션 정보를 청크 메타데이터로 살림 → [Prompt_0508.md](Prompt_0508.md)의 분류 프롬프트에 "이 청크가 속한 섹션" 컨텍스트 주입 가능
- 표는 가능한 한 한 청크에 보존, 부득이한 경우 줄(`\n`) 우선 절단
- 토큰 한계 초과는 마지막 단계에서만 강제 절단

**SemanticChunker는 비교군으로 1회 측정 후 제외**하는 것이 비용 대비 합리적.

---

## 6. 실험 설계 권장

1. **공통 입력 고정**: 동일 OCR 모델로 추출한 Markdown 문서 3종 (송장 / 표 중심 포장명세서 / 헤더 풍부한 선하증권)
2. **조건**: 4개 splitter × overlap (0% / 10% / 20%)
3. **정량 지표**:
   - 청크 수, 평균/최대 토큰 길이
   - **표 무결성 점수**: (보존된 표 행 수 / 원본 표 행 수), 헤더 행 보존 여부
   - 헤더 메타데이터 부착률
   - 처리 시간
4. **정성 지표**: 동일 문서를 분류 프롬프트로 분류했을 때 정답률 (splitter별 top-k 청크를 컨텍스트로 사용)
5. **표 단위 비분할 옵션**: Markdown 표(`|...|...|`) 영역을 사전 추출하여 한 청크로 묶는 전처리 — splitter와 직교하는 개선책으로 함께 측정

위 설계로 가면 보고서에 "왜 이 조합인가"의 근거가 정량적으로 남는다.
