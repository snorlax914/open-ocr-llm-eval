# 감자빵 4주차 보고서 — 카테고리 추천 모델 재검증 및 RAG 기반 마크다운 Chunking 전략 수립

3주차 보고서에서 Qwen3-4B의 응답 시간이 8B 대비 약 4.5배 느린 비정상적 결과가 확인됐고, 이는 Instruct가 아닌 Thinking(하이브리드)을 사용한 결함으로 진단됐다. 또한 새 카테고리 명명에서 "기타"·"확인서" 같은 모호한 이름이 발생할 가능성이 지적됐고, RAG 검색 단계로 이어지는 Markdown Chunking 전략이 미정 상태였다. 4주차에서는 (1) Qwen3-4B-Instruct 기준 4B vs 8B 재벤치마킹, (2) 영문 프롬프트 v2 고도화(한국어 출력 강제 + 명명 규칙 강화 + 길이 압축), (3) 4종 Splitter 비교, (4) Overlap 비율·Separator 정책 탐색을 진행했다.

## 2. 모델 효율성 및 지시 이행력 재검증 (4B-Instruct vs 8B)

### 2.1. 결함 진단 — 3주차 4B 결과의 원인

3주차 보고서 5의 4B 결과(Core Accuracy 0.359~0.462, Avg Latency 3,400ms)는 Ollama 기본 태그 `qwen3:4b`가 하이브리드 이었기 때문이다. Hybrid 모델은 `think=False` 옵션과 `/no_think` 디렉티브를 무시하고 reasoning preamble("Okay, let's tackle this...")부터 출력했고, `num_predict=256`이 다 차서 결국 답변에 도달하지 못한 채 잘렸다. 파서가 reasoning 본문에서 라벨 substring을 회수했기 때문에 사실상 무작위에 가까운 정확도가 나왔다.

→ **수정**: `MODEL_CONFIG["qwen3-4b"].model_id`를 `qwen3:4b` → **`qwen3:4b-instruct`** 로 교체. 또한 `OllamaRunner`에서 `/no_think` 디렉티브 주입을 hybrid 변종에만 적용되도록 좁혔다(instruct/thinking 변종은 디렉티브가 chat template에 없어 user message 말미에 평문으로 노출되는 부작용 방지).

### 2.2. 4B-Instruct 단독 검증 (v1 프롬프트 기준)

수정 직후 동일 v1 프롬프트로 4B-Instruct 재측정:

| 변종 | ko Core Acc | en Core Acc | Avg Latency |
|---|---:|---:|---:|
| `qwen3:4b` (hybrid, 3주차) | 0.462 | 0.359 | ~3,400 ms |
| **`qwen3:4b-instruct` (4주차)** | **0.974** | **1.000** | **~560 ms** |

정확도 +51~64%p, 지연 1/6 수준으로 개선. **3주차 결론은 잘못된 모델 측정에 기반한 것이었음이 확정됐다.** Reasoning 잔존 문제도 출력에서 완전히 사라졌다(raw 출력이 `상업송장` 한 줄로 깨끗).

### 2.3. v2 프롬프트 기준 4B-Instruct vs 8B 재벤치마킹

3에서 도출된 v2 프롬프트로 두 모델을 동일 조건(Ollama, temperature=0, num_predict=256)에서 EN 프롬프트로 측정:

| 지표 | Qwen3-8B | Qwen3-4B-Instruct | 차이 |
|---|---:|---:|---:|
| Core Accuracy (n=39) | **1.000 (39/39)** | 0.821 (32/39) | +0.179 (8B 우세) |
| Avg Latency | 902 ms | **624 ms** | −278 ms (4B가 1.45× 빠름) |
| Parse fail | 0 | 0 | 0 |

**Per-class F1 (4B-Instruct)**: 상업송장 0.800 / 포장명세서 0.957 / **선하증권 0.000** / 원산지증명서 1.000

**Per-class F1 (8B)**: 4 클래스 모두 **1.000**

→ 4B-Instruct는 **선하증권 6장을 모두 상업송장으로 오분류**하는 모드 실패가 발생했다. 출력은 `카테고리: 상업송장` 한 줄로 형식 자체는 깨끗하므로 파서 문제가 아니라 **모델의 라벨 의미 식별 실패**다.

### 2.4. VRAM 점유율

Windows 환경 한계로 정확한 측정은 어렵지만, Q4_K_M 가중치 크기 기준으로 추정·확인:

| 모델 | Q4_K_M 크기 (Ollama) | 실측 VRAM (개략) |
|---|---:|---:|
| Qwen3-4B-Instruct | ~2.5 GB | ~2.7 GB |
| Qwen3-8B | ~5.2 GB | ~5.0 GB |

### 2.5. 결론 — MVP 운영 모델 권장

> **Qwen3-8B 채택 권장.**

근거: 4B-Instruct의 **선하증권 0% 회귀(F1=0)** 가 결정적이다. 단순 정확도 하락이 아니라 **특정 카테고리 자체를 인식하지 못하는 모드 실패**로, 운영 신뢰성을 근본적으로 훼손한다. 메모리 −2.7GB·속도 1.45× 우위로는 보상이 어렵다. 자세한 비교는 [`4b_vs_8b_비교.md`](../../week3/report/4b_vs_8b_비교.md) 참조.

→ 4B-Instruct는 (a) v2 프롬프트에 [Category Reference] 한 줄 설명을 다시 추가한 v2.1로 재측정하거나, (b) 도메인 LoRA 파인튜닝 후 재검토 시에만 운영 후보로 다시 검토.

## 4. 마크다운 Chunking 전략 탐색

### 4.1. 실험 환경

OCR(PaddleOCR-VL-1.5)로 추출된 마크다운 문서 92개(물류 52 + 은행 40, 은행은 참고용)에서 6개 샘플을 선정해 4종 Splitter + Hybrid 1종을 비교했다. 환경 / 데이터 / 샘플 선정 근거는 [`week4_chunking_report.md`](../week4_chunking_report.md) 실험 개요 참조.

| 항목 | 설정 |
|---|---|
| 라이브러리 | langchain-text-splitters 1.1.2, langchain-experimental 0.4.1, tiktoken 0.12.0 |
| 토크나이저 | cl100k_base (tiktoken) |
| 임베딩 (SemanticChunker) | sentence-transformers/all-MiniLM-L6-v2 |
| 기본 설정 | chunk_size=1500자, chunk_overlap=200자 |

### 4.2. 4종 Splitter 비교 (물류 5개 샘플 평균)

| Splitter | 청크 수 | 평균 청크 길이 | 표 무결성 | 속도 |
|---|---:|---:|---:|---:|
| RecursiveCharacterTextSplitter | 4.6 | 982자 / 312tok | 0% | 0.001s |
| MarkdownHeaderTextSplitter | 1.0 | 3,685자 / 1,166tok | **100%** | 0.001s |
| TokenTextSplitter | 7.2 | 664자 / 217tok | 0% | 0.07s |
| SemanticChunker | 1.6 | 2,301자 / 703tok | 40% * | 6.2s |
| **Hybrid (MdHeader→Recursive)** | 4.0 | 1,170자 / 374tok | 0% | 0.001s |

> *SemanticChunker의 표 무결성 40%는 분할이 거의 일어나지 않은 결과(상업송장 2건이 1청크로 남음). 실제로 분할이 발생한 3건은 모두 0%.

### 4.3. Splitter별 평가 요약

| Splitter | 장점 | 단점 | 물류 적합도 |
|---|---|---|:---:|
| RecursiveChar | 가장 빠름, 자연스러운 문단 분할 | HTML `<table>` 인식 못 해 표 중간 절단 (표 무결성 0%) | △ |
| MarkdownHeader | 표 무결성 100%, 헤더 메타데이터 자동 부착 | 물류 문서에 마크다운 헤더가 거의 없어 분할이 일어나지 않음 (1청크) | X |
| TokenSplitter | 토큰 단위 정밀 제어 | 표 행·문장 가차없이 절단, 청크 수 최다 | X |
| SemanticChunker | 의미 전환 지점 분할 | 5~28초로 압도적으로 느림, HTML 표 임베딩 잡지 못해 엉뚱한 위치 절단 | X |

### 4.4. 핵심 발견

**물류 문서는 (1) HTML `<table>` 블록이 본문의 거의 전부이고 (2) 마크다운 `#`/`##` 헤더가 거의 없다.** 이 두 특성 때문에 4종 splitter 어느 것도 단독으로는 표를 보존하면서 적절한 크기로 분할하지 못한다:

- RecursiveChar / Token / Semantic → HTML `<table>` 중간 절단
- MarkdownHeader → 헤더가 없어 분할 자체가 안 일어남(1청크)

→ **기존 langchain Splitter 단독으로는 물류 도메인 RAG에 부적합**하다. HTML Table-aware 전처리(`<table>~</table>` 블록 사전 추출 후 단일 청크 보존)가 직교 전략으로 필요하다.

자세한 청크 내용 예시 / 은행 문서 비교 / 종합 비교표는 [`week4_chunking_report.md`](../week4_chunking_report.md) §과제 3 참조.

## 5. Chunking 시 Overlap 전략 탐색

### 5.1. 실험 설계

권장 파이프라인(MarkdownHeader → Recursive)을 고정하고 8조건 교차 측정:

| 조건 | Overlap | Separator 정책 |
|:---:|:---:|---|
| A1~A4 | 0% / 10% / 20% / 30% | 기본 |
| B1~B4 | 0% / 10% / 20% / 30% | 기본 + `\n|` 추가 |

측정 지표: 표 무결성, 깨진 표 수, 표 헤더 복제율, 키워드 보존율, 토큰 비용 증가율.

### 5.2. 결과 (물류 문서, chunk_size=1500)

| Overlap | 청크 수 | 토큰 비용 증가 | 표 무결성 | 표 헤더 복제율 | 키워드 보존율 |
|:---:|---:|---:|---:|---:|---:|
| 0% | 3.6 | 기준선 | 0% | 0% | 93% |
| 10% | 3.8 | +7.3% | 0% | 0% | 93% |
| 20% | 4.0 | +14.4% | 0% | 0% | 93% |
| 30% | 4.0 | +22.6% | 0% | 0% | 93% |

### 5.3. 표 강제 분할 시나리오 (chunk_size=800, 물류)

표가 반드시 분할되도록 chunk_size를 800자로 줄여 Overlap 효과 관찰:

| 샘플 | 0% | 20% | 20% + `\n|` |
|---|---|---|---|
| 상업송장(소) | 5청크, 무결성 0% | 6청크, 무결성 0% | 6청크, 무결성 0% |
| 상업송장(대) | 8청크, 무결성 0% | 8청크, 무결성 0% | 8청크, 무결성 0% |
| 포장명세서 | 4청크, 무결성 0% | 4청크, 무결성 0% | 4청크, 무결성 0% |
| 선하증권(대) | 7청크, 무결성 0% | 9청크, 무결성 0% | 9청크, 무결성 0% |
| 원산지증명서 | 7청크, 무결성 0% | 8청크, 무결성 0% | 8청크, 무결성 0% |

### 5.4. 핵심 발견

1. **Overlap 비율을 0%에서 30%까지 올려도 표 무결성·헤더 복제율은 변화 없음.** 토큰 비용만 +7~29% 증가.
2. **A 조건(기본)과 B 조건(`\n|` separator 추가) 결과가 전 샘플에서 동일.** 이유는 `\n|`이 마크다운 파이프 테이블(`| 품목 | 수량 |`)을 전제한 separator인데, **PaddleOCR-VL의 실제 출력은 HTML `<table>` 태그**라 `\n|` 구분자가 문서 내에 존재하지 않기 때문.
3. **HTML `<table>` 블록은 줄바꿈 없는 하나의 긴 문자열로 출력**되므로, 문자/줄 단위 Overlap으로는 표 구조를 복원할 수 없다. 

### 5.5. 결론 — Overlap만으로는 부족하다

> **HTML 테이블 보존은 Overlap·Separator 정책으로 풀 수 없는 문제이며, 분할 전 단계의 Table-aware 전처리가 필요하다.**

권장 파이프라인 (직교 전략 결합):

```
OCR 마크다운
  → [1단계] HTML <table>~</table> 블록 추출 → 단일 청크로 보존
  → [2단계] 테이블 외 영역만 RecursiveCharacterTextSplitter로 분할 (overlap 20%)
  → [3단계] 테이블이 chunk_size 초과 시, <tr> 행 단위로 분할 + 헤더 행(<tr> 첫 번째) 복제
  → [4단계] 토큰 한계 초과 시 TokenTextSplitter 안전망 (overlap 10%)
```

자세한 분석 / 은행 문서 결과 / Separator별 효과 분석은 [`week4_chunking_report.md`](../week4_chunking_report.md) §과제 4 + [`overlap_strategy_analysis.md`](../overlap_strategy_analysis.md) 참조.

## 6. Splitter 선택 가이드

| 상황 | 권장 |
|---|---|
| 물류 문서 (현재 OCR 출력 그대로) | **HTML Table-aware 전처리 + RecursiveChar (overlap 20%)** |
| OCR 후처리로 마크다운 헤더 추가 시 | MarkdownHeader → RecursiveChar 하이브리드 |
| 토큰 한계 안전망 | TokenTextSplitter (마지막 단계에서만) |
| 평문 위주 문서 | RecursiveChar 단독으로 충분 |

## 7. 결론 및 후속 과제

### 7.1. 4주차 성과

- 3주차 4B vs 8B 비교의 결함(하이브리드 변종 사용)을 진단·수정해 **`qwen3:4b-instruct`** 기준 재벤치마킹 완료. 4B-Instruct ko 0.974 / en 1.000 (v1), v2에서는 8B 1.000 vs 4B-Instruct 0.821(선하증권 회귀)로 **8B 채택 권장 결론** 도출.
- 영문 프롬프트 v2 설계·검증: 1,600~2,000 → 550~750 토큰(약 60% 감소), 한국어 출력 강제·새 카테고리 명명 규칙 강화 적용. 8B Core Accuracy 0.974 → 1.000으로 1건 회복.
- langchain-text-splitters 4종 + Hybrid 비교, 물류·은행 도메인 6개 샘플 정량 평가. **MarkdownHeader는 표를 보존하지만 분할이 안 되고, 나머지는 표 보존 0%** 라는 한계 정량 확인.
- Overlap 0~30% × Separator 정책 8조건 측정. **Overlap·Separator로는 HTML 테이블 보존 불가능, Table-aware 전처리 필수** 결론 도출.
- `parse_label`에 `신규 카테고리:` 접두사 처리 추가, `OllamaRunner`의 `/no_think` 디렉티브 적용 범위를 hybrid 변종으로 좁힘.

### 7.2. 후속 과제

1. **v2.1 프롬프트 측정**: [Category Reference] 한 줄 설명을 v2에 다시 추가하여 4B-Instruct의 선하증권 회귀가 해소되는지 확인. 동시에 8B에는 부담이 없는지 측정.
2. **8B 거부율 보강**: v2가 `분류 불가`를 한 번도 사용하지 않는 문제(0/13). "확신 없으면 분류 불가 우선" 지시를 추가한 변종 측정.
3. **HTML Table-aware 전처리 파이프라인 구현**: §5.5의 4단계 파이프라인을 실제 코드로 구현하고, 기존 splitter 단독 사용 대비 **표 보존율** 및 **분류 LLM 정답률** 개선을 정량 비교.
4. **마크다운 파이프 테이블 변환 후 재실험**: PaddleOCR-VL 출력의 HTML `<table>`을 `| col1 | col2 |` 형식으로 후처리한 뒤 동일 Overlap·Separator 실험을 재수행하여 `\n|` separator 효과를 정확히 측정.
5. **Overlap이 LLM 답변 품질에 미치는 영향 측정**: 본 실험은 표 무결성·키워드 보존 등 구조적 지표만 측정했으므로, overlap 비율별 청크를 분류 프롬프트에 입력하여 정답률·요약 품질 변화를 정성·정량으로 확인.
6. **MVP FastAPI 서비스 통합**: Qwen3-8B + v2(또는 v2.1) 프롬프트 + Table-aware 청킹 파이프라인을 묶어 OCR → Chunking → 분류 → RAG 검색의 경량 iDOCS MVP로 통합.
