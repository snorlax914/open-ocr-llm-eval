# 4주차 — 마크다운 Chunking 전략 실험 보고서

## 실험 개요

OCR(PaddleOCR-VL)로 추출된 마크다운 문서를 LLM이 잘 이해할 수 있는 단위로 분할하기 위해, langchain-text-splitters의 4가지 Splitter를 비교하고 Overlap 전략이 품질에 미치는 영향을 탐색했다.

### 실험 환경

- **라이브러리**: langchain-text-splitters 1.1.2, langchain-experimental 0.4.1, tiktoken 0.12.0, sentence-transformers 5.4.1
- **토크나이저**: cl100k_base (tiktoken)
- **임베딩 모델** (SemanticChunker): sentence-transformers/all-MiniLM-L6-v2
- **기본 설정**: chunk_size=1500자, chunk_overlap=200자

### 전체 데이터 현황

OCR 출력 데이터는 PaddleOCR-VL 모델로 추출된 마크다운 파일 **총 92개**이다.

## 과제 3: 4가지 Splitter 비교

### 3-1. 물류 문서 결과

| Splitter | 청크 수 (평균) | 평균 청크 길이 | 표 무결성 | 속도 |
|----------|:---:|:---:|:---:|:---:|
| **RecursiveCharacterTextSplitter** | 4.6개 | 982자 / 312tok | **0%** | 0.001s |
| **MarkdownHeaderTextSplitter** | 1.0개 | 3,685자 / 1,166tok | **100%** | 0.001s |
| **TokenTextSplitter** | 7.2개 | 664자 / 217tok | **0%** | 0.07s |
| **SemanticChunker** | 1.6개 | 2,301자 / 703tok | **40%*** | 6.2s |
| **Hybrid (MdHeader→Recursive)** | 4.0개 | 1,170자 / 374tok | **0%** | 0.001s |

> *SemanticChunker 표 무결성 40%는 상업송장 2건이 분할되지 않고 1청크로 남아 100%로 집계된 결과. 실제로 분할이 발생한 3건(포장명세서/선하증권/원산지증명서)은 모두 0%.

**청크 내용 예시 — 상업송장(소)에서 RecursiveChar vs MarkdownHeader 비교:**

RecursiveChar는 HTML 테이블을 3개 청크로 절단한다. 두 번째 청크가 테이블 중간(`<td>` 속성 사이)에서 시작:
```html
<!-- 청크 2 시작 -->
<table border=1 style='margin: auto; word-wrap: break-word;'><tr><td rowspan="2" colspan="4">Exporte...
<!-- 청크 3 시작 (테이블 중간에서 잘림) -->
25-Jan-2004</td></tr><tr><td colspan="2">Port of Discharge ARBRA, SWEDEN</td><td colspan="2">Final D...
```

반면 MarkdownHeader는 문서 전체를 1청크로 유지하여 `<table>~</table>` 구조가 온전하지만, 분할 자체가 일어나지 않음.

### 3-2. 은행 문서 결과 (참고)

| Splitter | 청크 수 | 평균 청크 길이 | 표 무결성 | 속도 |
|----------|:---:|:---:|:---:|:---:|
| **RecursiveChar** | 10개 | 900자 / 381tok | 33.3% | 0.001s |
| **MarkdownHeader** | 2개 | 4,119자 / 1,707tok | **100%** | 0.001s |
| **TokenSplitter** | 26개 | 392자 / 162tok | 12.5% | 0.004s |
| **SemanticChunker** | 2개 | 4,113자 / 1,703tok | 0% | 6.3s |
| **Hybrid** | 10개 | 916자 / 396tok | 33.3% | 0.003s |

### 3-3. 각 Splitter 평가

#### i. RecursiveCharacterTextSplitter

- **장점**: 가장 빠르고 구현 단순. 문단/줄바꿈 우선순위로 자연스러운 분할
- **단점**: HTML `<table>` 블록을 인식하지 못해 테이블 중간에서 절단. 물류 문서 전 샘플에서 표 무결성 0%
- **적합성**: 평문 위주 문서에는 무난하지만, **표가 핵심인 물류 문서에 단독 사용 부적합**

#### ii. MarkdownHeaderTextSplitter

- **장점**: 표 무결성 100%. 헤더 메타데이터(`H1`, `H2`)를 자동 부착하여 섹션 소속 정보 보존
- **단점**: 물류 문서 대부분 마크다운 헤더(`#`, `##`)가 없어 **문서 전체가 1청크로 나옴** → 사실상 분할이 일어나지 않음. 은행 신청서처럼 `##` 헤더가 있는 경우에만 유의미한 분할(2청크)
- **적합성**: 헤더가 있는 문서에는 강력하나, **현재 PaddleOCR-VL의 물류 문서 출력에는 헤더가 거의 없어 실효성 낮음**. OCR 모델이 헤더를 생성하도록 후처리를 추가하거나, 다른 OCR 모델 사용 시 재평가 필요

#### iii. TokenTextSplitter

- **장점**: 토큰 단위 정밀 제어로 LLM 컨텍스트 한계와 1:1 매칭. 임베딩 모델에 맞는 청크 크기 보장
- **단점**: 표 행·문장 가차없이 토큰 경계에서 절단. 물류 문서 전 샘플 표 무결성 0%, 은행 신청서도 12.5%. 청크 수가 가장 많아 정보 분산 심함
- **적합성**: **단독 사용 부적합**. 다른 splitter 결과가 토큰 한계를 넘을 때 마지막 안전망으로 결합하는 용도에만 가치

#### iv. SemanticChunker

- **장점**: 의미적 전환 지점에서 자연스럽게 분할. 상업송장 2건에서 문서를 쪼개지 않고 1청크로 유지한 점은 문서 전체가 단일 주제임을 인식한 결과
- **단점**: **압도적으로 느림** (5~28초, 다른 splitter의 수천 배). 실제 분할이 발생한 3건(포장명세서/선하증권/원산지증명서)은 표 무결성 전부 0%. HTML 표 행은 임베딩이 잘 잡지 못해 엉뚱한 위치에서 분할. 청크 크기 불균일(한 청크 4,485자 vs 다른 청크 976자)
- **적합성**: **물류 문서에 부적합**. 표 무결성 40%는 분할을 안 한 덕이지 표를 보존한 것이 아님. 비교군 이상의 가치 없음

### 3-4. 종합 비교표

| Splitter | 표 보존 | 헤더 보존 | 의미 보존 | 토큰 효율 | 속도 | 물류 적합도 |
|----------|:---:|:---:|:---:|:---:|:---:|:---:|
| RecursiveChar | X | X | △ | △ | **◎** | △ |
| MarkdownHeader | **◎** | **◎** | ◎ | X (1청크) | **◎** | X (헤더 없음) |
| TokenSplitter | X | X | X | **◎** | ○ | X |
| SemanticChunker | X | X | ○ | △ | X | X |
| **Hybrid** | X | ○ | △ | △ | **◎** | △ |

> **핵심 발견**: 물류 문서는 (1) HTML 테이블이 본문의 거의 전부이고 (2) 마크다운 헤더가 없다. 이 두 특성 때문에 **기존 splitter 어느 것도 단독으로는 표를 보존하면서 적절한 크기로 분할하지 못한다**.

### 4-4. Separator 정책 효과

> **A 조건(기본)과 B 조건(`\n|` 추가)의 결과가 전 샘플에서 완전히 동일했다.**

이유: `rag_chunking_analysis.md`에서 권장한 `\n|` separator는 **마크다운 파이프 테이블**(예: `| 품목 | 수량 |`)을 전제한 것이다. 그러나 PaddleOCR-VL의 실제 출력은 **HTML `<table>` 태그** 형식이므로 `\n|` 구분자가 문서 내에 존재하지 않아 효과가 없다.

chunk_size를 800자로 줄여 표가 반드시 분할되는 상황을 만들어 Overlap 효과를 관찰했다.

| 상업송장(대) | 8청크, 표무결성 0% | 8청크, 표무결성 0% | 8청크, 표무결성 0% |
| 포장명세서 | 4청크, 표무결성 0% | 4청크, 표무결성 0% | 4청크, 표무결성 0% |
| 선하증권(대) | 7청크, 표무결성 0% | 9청크, 표무결성 0% | 9청크, 표무결성 0% |

## 종합 분석 및 제안

### 핵심 발견

1. **기존 splitter는 HTML 테이블을 구조적으로 인식하지 못한다**. RecursiveChar, Token, Semantic 모두 `<table>~</table>` 블록 중간을 가차없이 절단한다.

2. **MarkdownHeader는 표를 보존하지만 분할이 안 된다**. 물류 문서 5개 중 4개가 마크다운 헤더 없이 HTML 테이블만으로 구성되어, 문서 전체가 1청크로 나온다.

3. **Overlap 비율을 올려도 HTML 테이블 보존에는 효과 없다**. 토큰 비용만 증가(30%에서 +22~29%)하고 표 무결성은 고정.

4. **`\n|` separator 전략은 무효**. PaddleOCR-VL 출력이 마크다운 파이프 테이블이 아닌 HTML 테이블이기 때문.

### 제안: HTML Table-aware 전처리 필요

기존 langchain splitter만으로는 한계가 명확하므로, **분할 전 HTML 테이블 영역을 사전 처리하는 파이프라인**이 필요하다:

```
OCR 마크다운
  → [1단계] HTML <table>~</table> 블록 추출 → 단일 청크로 보존
  → [2단계] 테이블 외 영역만 RecursiveCharacterTextSplitter로 분할
  → [3단계] 테이블이 chunk_size 초과 시, <tr> 행 단위로 분할 + 헤더 행(<tr> 첫 번째) 복제
```

이 접근은 `overlap_strategy_analysis.md`에서도 "Overlap만으로는 부족하다"며 직교 전략으로 권장한 바와 일치한다. 실험 결과가 이를 정량적으로 확인해 주었다.

### Splitter 선택 가이드

| 상황 | 권장 |
|------|------|
| 물류 문서 (현재 OCR 출력 그대로) | HTML Table-aware 전처리 + RecursiveChar |
| OCR 후처리로 마크다운 헤더 추가 시 | MarkdownHeader → RecursiveChar 하이브리드 |
| 토큰 한계 안전망 | TokenTextSplitter (마지막 단계에서만) |
| 평문 위주 문서 | RecursiveChar 단독으로 충분 |

## 향후 수행점

본 실험에서 확인하지 못했거나 추가 검증이 필요한 항목을 정리한다.

1. **Overlap이 LLM 답변 품질에 미치는 영향 측정**: 현재 실험은 표 무결성·키워드 보존 등 구조적 지표만 측정했다. 실제로 overlap 비율별 청크를 LLM에 입력하여 분류 정답률이나 요약 품질이 달라지는지 정성적·정량적으로 확인하는 실험이 필요하다.

2. **마크다운 파이프 테이블 변환 후 재실험**: PaddleOCR-VL 출력이 HTML `<table>` 형식이어서 overlap과 `\n|` separator의 표 복원 효과를 검증할 수 없었다. OCR 후처리로 HTML 테이블을 마크다운 파이프 테이블(`| col1 | col2 |`)로 변환한 뒤, 동일 실험을 재수행하면 overlap의 표 헤더 복제 효과를 정확히 측정할 수 있다.

3. **HTML Table-aware 전처리 파이프라인 구현 및 검증**: 종합 제안에서 제시한 `<table>` 블록 사전 추출 → `<tr>` 행 단위 분할 + 헤더 복제 전략을 실제 구현하고, 기존 splitter 단독 사용 대비 표 보존율 및 LLM 답변 품질 개선을 정량 비교해야 한다.
