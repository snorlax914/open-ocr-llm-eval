## **2. 회의 내용**

---

### **1. LLM 모델 재검증 방향** 

- 기존 테스트 결과 재검토 필요
기존 VRAM 점유율내용:
    Windows 환경에서는 정확한 측정 제한
    현재 약 2.7GB 수준 확인
    8B 모델은 약 5GB 수준 예상

- 피드백:
4B 모델이 8B보다 4~5배 느린 결과는 비정상적
- 원인:
Instruct 모델이 아닌 Thinking 모델 사용 가능성
=> Qwen3:4B-Instruct 모델 기준으로 재실험 필요

+) 추가 검토:
VRAM 점유율 + 응답 속도 + 지시 이행력 재확인

### **2. 프롬프트 개선 방향**

- 기존 문제:
    프롬프트 길이가 길어 토큰 과다 사용 -> 응답 속도 저하 가능성
    새 카테고리 생성 시 "기타", "확인서" 등 모호한 이름 출력 가능

- 개선 방향:
    프롬프트 본문은 영문 유지
    결과 출력은 기존 카테고리, 신규 카테고리 모두 한국어 출력
    카테고리 명명 규칙 강화 - 모호한 표현 금지
    (선택) 프롬프트 길이 압축

### **3. RAG 기반 Markdown Chunking 전략 탐색**

- Chunking 목적: OCR 결과 Markdown 데이터를 효율적으로 분할하여 임베딩 품질 + 문맥 유지 최적화

- 현재 사용 중인 방식
    - RecursiveCharacterTextSplitter
    - chunk size: 1500
    - overlap: 최대 200자
    - separator: 헤더, 문단, 줄바꿈 등

- 탐색 대상  
    - Fixed-size Chunking (문자 수 기준)  
    - MarkdownHeaderTextSplitter  
    - RecursiveCharacterTextSplitter  
    - TokenTextSplitter (토큰 기준: Fixed-size 확장형이라 과제에서는 픽스를 뺀듯?) 
    - SemanticChunker  

- 비교 요소: 정보 밀도, 문맥 유지, 표 구조 보존, 속도, 구현 난이도 등..

### **4. Overlap 전략 탐색**

- 목적: 청크 간 정보 단절 최소화

- 탐색 요소:
    Overlap 비율: 10%, 20%, 기타
    답변 품질 변화
    Markdown 표 데이터 손실 방지 효과
    문맥 복원 성능 등...

### **5. 서비스 구현 및 MVP 방향**

- 최종 목표: OCR + 카테고리 분류 + RAG 검색 통합된 경량 iDOCS 서비스 구축

- 일정: 약 7주차 소형 플랫폼 형태 목표로, 어려울 경우 8주차까지 보고서 중심 결과물 전환 가능

- 구현 범위: 실무형 전체 서비스 수준은 현실적으로 어려움 
-> 시간 및 환경상 완전한 실무형 구현보다 기능별 핵심 파이프라인 구현 중심
-> 파이프라인 + 샘플 서비스 수준 + DB 스키마 및 구조 이해 중심
