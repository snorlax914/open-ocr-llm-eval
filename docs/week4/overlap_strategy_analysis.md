# Overlap 전략 탐색 분석

## 1. 분석의 출발점 — Overlap이 풀어야 할 문제

이전 분석([rag_chunking_analysis.md](rag_chunking_analysis.md))에서 권장한 **`MarkdownHeader → Recursive → Token` 3단 파이프라인**은 "어디서 자를지"를 정한다. Overlap은 그 다음 질문, 즉 **"잘린 경계에서 정보 단절을 어떻게 보완할지"**를 푸는 장치다.

이 프로젝트 맥락에서 Overlap이 직접 영향을 주는 지점은 다음 세 가지다.

- **분류 단서의 경계 손실 방지**: [Prompt_0508.md](Prompt_0508.md)는 "INVOICE", "Country of Origin" 같은 키워드와 전체 맥락을 함께 활용한다. 이 키워드가 청크 경계에 걸리면 양쪽 청크 모두 약한 단서만 가지게 됨 → Overlap이 키워드를 양쪽에 모두 남겨야 함
- **표 헤더 행 복원**: 무역 문서의 핵심인 품목 표가 두 청크로 나뉠 때, 두 번째 청크에 컬럼 헤더(`| 품목 | 수량 | 단가 |`)가 없으면 셀 값만 남아 의미 추론 불가 → Overlap이 헤더 행을 복제해야 함
- **다중 카테고리 판단 보존**: [Prompt_0508.md](Prompt_0508.md)의 "ONLY when clearly serves two purposes simultaneously" 조건은 두 목적이 한 컨텍스트에 함께 보여야 성립. 청크가 쪼개지면 각 청크가 단일 카테고리로만 보이게 됨 → Overlap이 인접 섹션의 일부를 끌어와 "이 섹션 옆에 무엇이 있었는지" 단서를 남겨야 함

→ Overlap 평가축은 다음 4가지로 정리한다.
**(1) 키워드 경계 보존 (2) 표 헤더 복제율 (3) 토큰 비용 증가율 (4) 중복 정보로 인한 검색 노이즈**

---

## 2. Overlap 비율별 트레이드오프

### 0% (no overlap)
- **장점**: 토큰 비용 최소, 검색 시 동일 정보 중복 없음 (top-k가 다양한 섹션을 커버)
- **단점**:
  - 표가 두 청크에 걸치면 두 번째 청크는 헤더 행 없이 데이터 행만 남음 → **분류 LLM이 "수량/금액 표"인지 "포장 명세 표"인지 구분 불가**
  - 경계에 걸친 키워드(예: "Certificate of **Origin**" 중 "Origin"만 다음 청크로 넘어감) 손실
- **언제 적합**: MarkdownHeader 1차 분할 결과가 모두 토큰 한계 이내라 2차 분할이 거의 발생하지 않을 때

### 10% (보수적)
- **장점**: 토큰 비용 거의 동일, 짧은 키워드/문장 경계 손실은 대부분 복구
- **단점**:
  - 무역 문서의 표 헤더 행은 보통 청크 시작부에 위치하는 경우가 많음 → 10%(예: 1500자 중 150자) overlap으로는 **표 헤더 행 복제 보장 안 됨**
  - 표 헤더 행 자체가 150자를 넘는 다중 컬럼 표(품목·수량·단가·금액·HS코드…)에서는 효과 미미
- **언제 적합**: 평문 비중이 높은 문서, 표가 작거나 적은 경우

### 20% (균형)
- **장점**:
  - 표 헤더 행(보통 30~120자) + 직전 1~2개 데이터 행이 안전하게 복제됨 → **두 번째 청크가 표 구조를 자체적으로 복원 가능**
  - 키워드 + 그 키워드의 수식 문맥(앞 한 문장)이 함께 살아남음
  - [Prompt_0508.md](Prompt_0508.md)의 다중 카테고리 판단에 필요한 "인접 섹션 시그널"이 들어옴
- **단점**:
  - 토큰 비용 약 +20% (임베딩/검색/LLM 컨텍스트 모두에 영향)
  - 중복 정보로 인한 top-k 검색 노이즈 증가 — 같은 표 헤더가 여러 청크에 들어가면 동일 쿼리에 두 청크가 함께 매칭되어 다양성 저하
- **언제 적합**: 표·헤더 의존도가 높은 무역 문서 — **이 프로젝트의 주력 후보**

### 30%+ (공격적)
- **장점**: 거의 모든 경계 손실 복구
- **단점**:
  - 비용/노이즈 증가가 가파름. 1500자 청크에 450자 overlap이면 실질 신규 정보는 1050자 → **임베딩·검색 효율 1/3 감소**
  - 중복으로 인한 top-k 다양성 저하가 심각해져 RAG 검색 품질이 오히려 하락할 수 있음
- **언제 적합**: 표 한 개가 매우 크고(1500자 이상) 청크 중간을 넘나드는 특수한 문서 — 일반 권장 범위 아님

---

## 3. 비율 외 변수 — Overlap을 "어디서" 자르는가

비율 못지않게 중요한 것이 **overlap 경계 정책**이다. RecursiveCharacterTextSplitter의 separator 우선순위를 어떻게 두느냐에 따라 같은 20% overlap이라도 효과가 크게 달라진다.

| 경계 정책 | 표 헤더 보존 | 키워드 보존 | 구현 |
|---|---|---|---|
| 문자 단위(공백 무시) | ✕ (셀 중간 절단 가능) | △ | 기본값 |
| `\n` 우선 (줄 경계) | ◎ (표 행 단위 보존) | ○ | separator 조정 |
| `\n\n` 우선 (문단 경계) | ○ | ◎ | separator 조정 |
| `\n|` 우선 (표 행 명시) | ◎◎ (표 행 절대 안 잘림) | ○ | 커스텀 separator |

→ **Overlap 비율을 키우기 전에 separator 우선순위 조정이 더 비용 효율적**. 특히 `\n|`을 명시적으로 우선순위에 넣으면 10% overlap만으로도 20%에 가까운 표 보존 효과를 얻을 수 있다.

---

## 4. Overlap × Splitter 단계 결합

이전 권장안의 3단 파이프라인 각 단계에서 Overlap의 의미가 다르다.

- **1차 MarkdownHeaderTextSplitter**: Overlap 개념 자체가 거의 무의미 — 섹션 단위 분할이라 경계 손실보다는 헤더 메타데이터 부착이 핵심. **Overlap = 0**
- **2차 RecursiveCharacterTextSplitter**: 본격적으로 Overlap이 작동하는 구간. **이 단계에서만 비율 실험 진행**. 권장 separator: `["\n## ", "\n### ", "\n\n", "\n|", "\n", " ", ""]`
- **3차 TokenTextSplitter (안전망)**: 토큰 한계 초과 시에만 발동. Overlap을 작게(예: 10%) 두어 강제 절단의 정보 손실만 보완

---

## 5. 표 데이터 손실 방지 — Overlap만으로는 부족하다

Overlap은 "잘린 후 보완"이지만, **"애초에 표를 자르지 않는" 전처리**가 더 강력하다. 두 전략은 직교하며 함께 쓰는 것이 권장된다.

- **Table-aware preprocessing (전처리)**: Markdown 표(`|...|`로 시작하고 `|---|` 구분자를 가진 연속 블록)를 사전 식별 → **표 전체를 단일 청크로 강제 묶음**. 표가 chunk_size를 넘으면 그때만 행 단위로 분할하되 헤더 행을 모든 분할 청크에 복제
- **Overlap (사후 보완)**: 표 외 평문 영역의 경계 손실을 복구

→ 이 조합 하에서 Overlap의 "표 보존" 부담이 줄어들기 때문에 비율을 무리하게 키우지 않아도 된다(20% 수준에서 안정).

---

## 6. 종합 권장안

**파이프라인 결합 권장**:
- 1차 MarkdownHeader → overlap 0
- 2차 Recursive → **overlap 20%, separator에 `\n|` 명시**
- 3차 Token (안전망) → overlap 10%
- 직교 전처리: **Markdown 표 영역은 사전 추출 후 단일 청크로 보존, 분할 시 헤더 행 강제 복제**

**한 줄 요약**: **20% overlap을 기준선으로, separator 우선순위에 표 행 구분자(`\n|`)를 끼워넣는 것이 비율 증가보다 효율적**이다.

---

## 7. 실험 설계 권장

1. **공통 입력 고정**: 이전 분석과 동일한 무역 문서 3종 (송장 / 포장명세서 / 선하증권) — splitter 비교 실험과 데이터 셋 통일
2. **조건**: 권장 splitter 조합(MarkdownHeader → Recursive) 고정 × overlap (0% / 10% / 20% / 30%) × separator 정책 (기본 / `\n|` 추가) = **4 × 2 = 8 조건**
3. **정량 지표**:
   - **표 헤더 행 복제율**: (헤더 행이 살아있는 표 분할 청크 수 / 전체 표 분할 청크 수)
   - **경계 키워드 보존율**: 사전 정의 키워드 셋(INVOICE, B/L, Origin, Packing 등)이 잘릴 때 양쪽 청크 모두에 흔적이 남는 비율
   - 토큰 비용 증가율 (overlap 0% 대비)
   - top-k 검색 시 중복 청크 비율 (노이즈 지표)
4. **정성 지표**: 동일 분류 쿼리에 대해 [Prompt_0508.md](Prompt_0508.md) 적용 시 **다중 카테고리 판단 정확도** — Overlap이 "두 목적 동시 포함" 시그널을 살리는지 확인
5. **표 손실 시나리오 집중 측정**: chunk_size를 일부러 작게(예: 800자) 줄여 표가 강제 분할되는 상황을 만든 뒤, overlap 비율별로 두 번째 청크의 표 의미 복원 정도를 분류 프롬프트로 평가

이 설계는 보고서에 **"20%가 왜 기준선인가, 그리고 separator 정책이 비율보다 왜 더 중요한가"**를 정량으로 보여줄 수 있다.
